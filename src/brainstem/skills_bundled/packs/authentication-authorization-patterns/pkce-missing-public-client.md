## Symptom
A mobile app or SPA implements the OAuth2 authorization code flow (redirect to IdP, get a `code` back, exchange it for tokens) but doesn't send a `code_challenge` on the authorize request or a `code_verifier` on the token exchange. Because these are "public" clients -- no client secret can be kept confidential in a mobile binary or browser-delivered JS -- the authorization code alone is the only thing standing between an interceptor and a full token exchange; without PKCE, anything that can observe or intercept the redirect (a malicious app registering the same custom URL scheme on Android/iOS, a browser extension, a referrer leak) can grab the code and exchange it for tokens itself.

## Likely causes
1. **The flow was copied from a confidential-client (server-side web app) example** where a client secret provides this protection instead, and PKCE was never added when adapting the same flow for a mobile app or SPA that can't hold a secret.
2. **The IdP/OAuth library defaults to not requiring PKCE**, and the integrating team wasn't aware it was optional-but-necessary for their client type rather than universally optional.
3. **Custom URL scheme redirect on mobile isn't exclusively claimed** -- multiple apps can register the same custom scheme (e.g. `myapp://callback`) on some platforms, so a malicious app can receive the authorization code redirect intended for the legitimate app, and without PKCE that stolen code is immediately exchangeable.
4. **A "public" client was mistakenly issued a client secret and configured as confidential**, giving a false sense that the code-interception risk is covered by client-secret verification -- but the secret is embedded in a distributable binary/JS bundle, so it's not actually confidential and doesn't substitute for PKCE.
5. **Server-side token exchange proxy was added for other reasons (hiding the client secret) without realizing PKCE protects a different step** (the redirect/code-capture step) that a secret-hiding proxy alone doesn't address if the code interception happens before the app even calls the proxy.

## Diagnose
- Inspect the authorize request URL generated by the client: check for `code_challenge` and `code_challenge_method` parameters. Their absence means PKCE isn't being used at all.
- Inspect the token exchange request: check for a `code_verifier` parameter alongside the `code`. If the authorize step had a challenge but the exchange has no verifier (or vice versa), PKCE is partially/incorrectly implemented.
- For mobile apps, check the OS-level redirect handling: is it a custom URL scheme (interceptable by any app that registers the same scheme) or an OS-verified mechanism (Android App Links / iOS Universal Links, which are bound to a specific app via domain verification)? Custom schemes without PKCE are the highest-risk combination.
- Check the client registration/configuration on the IdP side: is this client marked as "public" (no secret, PKCE required) or "confidential" (has a secret)? A mobile/SPA client marked confidential with an embedded secret is a related misconfiguration worth flagging alongside missing PKCE.

## Fix
Implement PKCE on every public client's authorization code flow: generate a cryptographically random `code_verifier` per authorization attempt, derive a `code_challenge` from it (`S256` -- SHA-256 then base64url, not the weaker `plain` method), send the challenge on the authorize redirect, retain the verifier locally (never transmitted until the final step), and send it with the token exchange request; the IdP then confirms the verifier hashes to the challenge it recorded at authorize time before issuing tokens, so a stolen `code` alone is useless without the verifier that never left the legitimate client. Pair this with the strongest available redirect binding for the platform (Android App Links / iOS Universal Links over bare custom URL schemes) as defense in depth, since PKCE protects the token exchange even if the code itself is intercepted, but a verified redirect reduces how often interception can happen at all.

## Pitfalls
Using the `plain` PKCE method (sending the code verifier itself as the challenge, unhashed) instead of `S256` provides essentially no protection if the challenge is observable anywhere the code is -- always require `S256` and reject `plain` if the IdP supports it as a fallback. Also, treating a confidential-client secret as a PKCE substitute for a public client that technically has *a* secret configured (e.g. a mobile app shipping an embedded client secret) is a false sense of security, since that secret is extractable from the app binary and isn't actually confidential.

## Verify
Capture a legitimate authorization code from a real login flow (e.g. via a proxy/debugger) and attempt to exchange it for tokens directly, without the correct `code_verifier` -- confirm the IdP rejects the exchange. Then confirm the normal flow, with the correct verifier, still succeeds, and inspect the authorize request to confirm `code_challenge_method=S256` specifically (not `plain`).
