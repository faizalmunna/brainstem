## Symptom
An S3 pre-signed URL, generated by application code expecting it to be
valid for some window of time, fails when accessed -- either immediately
with `SignatureDoesNotMatch`, prematurely with `Request has expired`
well before the intended expiry, or with a plain `403 Forbidden` despite
the signature itself being accepted -- and the failure doesn't reproduce
consistently across environments (works when tested locally, fails in a
container/Lambda environment, or vice versa).

## Likely causes
1. **Clock skew on the machine/container generating the signed URL** --
   SigV4 signatures embed a timestamp, and if the signing environment's
   system clock is meaningfully off from real time (common in
   containers with a drifted clock, or a Lambda execution environment
   with an unusual clock source), the signature's embedded timestamp
   falls outside S3's acceptance window, producing `SignatureDoesNotMatch`
   or premature expiry even though the code's own "expires in N seconds"
   logic looks correct.
2. **A bucket policy or S3 Block Public Access setting overrides what
   the pre-signed URL would otherwise permit** -- a pre-signed URL only
   encodes that *the signing principal* is authorized; if the bucket
   policy has an explicit `Deny` for the relevant action/condition (e.g.,
   requiring a specific source VPC endpoint, denying non-TLS requests,
   or denying based on `aws:SourceIp`), that deny still applies and
   overrides the otherwise-valid signature, which surprises people who
   assume a valid signature is sufficient on its own.
3. **The URL's expiry was calculated correctly at generation time but the
   URL is cached/reused well past that window** -- e.g., a CDN or
   application cache serves a pre-signed URL value to multiple users or
   for longer than intended, and by the time a later user clicks it, the
   embedded expiry has passed.
4. **Credentials used to sign the URL expired or rotated between
   generation and use** -- if signed with temporary credentials (an
   assumed role's STS credentials) that themselves expire before the
   pre-signed URL's own expiry window elapses, the underlying credential
   expiry -- not the URL's `Expires` parameter -- is what actually fails
   the request.
5. **A reverse proxy, API gateway, or CDN in front of the request
   re-encodes or strips query string parameters** (the signature and its
   accompanying `X-Amz-*` parameters are all part of the query string),
   corrupting the signature before it ever reaches S3.

## Diagnose
- Check the actual system clock of the environment generating the URL
  against real UTC time (`date -u` compared against a trusted time
  source, or check NTP sync status) -- more than a few seconds of drift
  is enough to matter for SigV4.
- Decode the failing URL's query parameters
  (`X-Amz-Date`, `X-Amz-Expires`, `X-Amz-Credential`) directly and
  compute whether, at the actual time of the request, the URL should
  still be within its validity window -- this separates "expired as
  designed" from "rejected despite being within window."
- Check the bucket policy and S3 Block Public Access settings for any
  `Deny` statement with conditions (`aws:SourceIp`, `aws:SecureTransport`,
  `aws:sourceVpce`) that could apply independently of the pre-signed
  URL's own validity -- test by attempting the request from a context
  that satisfies vs. violates each condition.
- Check what credentials were active when the URL was signed
  (`X-Amz-Credential` in the URL encodes the access key ID and date) and
  cross-reference against the credential's actual expiry if it came from
  an assumed role, comparing against when the request was actually made.
- If the request path involves a proxy/CDN/gateway, fetch the URL
  directly against S3 (bypassing the intermediary) to isolate whether
  the intermediary is mutating the query string.

## Fix
Ensure the signing environment's clock is NTP-synced (standard on AWS
compute like EC2/Lambda/ECS Fargate, but worth explicit verification in
custom containers or on-prem signing services) so embedded SigV4
timestamps are accurate. Don't assume a pre-signed URL alone is
sufficient authorization if the bucket has restrictive policies --
design bucket policies to explicitly permit the conditions pre-signed
URLs will actually be used under (or scope pre-signed URL usage to
buckets without conflicting deny conditions). Generate pre-signed URLs
just-in-time for actual use rather than generating them far in advance
and caching/distributing them broadly, and set the `Expires` duration to
match real intended usage windows rather than an arbitrarily long value
that outlives the signing credentials. When signing with temporary
(assumed-role) credentials, ensure the credential's own remaining
lifetime exceeds the pre-signed URL's requested expiry, or re-sign closer
to time of use. Configure any intermediary (CDN, API gateway, load
balancer) to pass query strings through unmodified for paths serving
pre-signed URLs.

## Pitfalls
Extending the pre-signed URL's `Expires` value to a very large number
"to stop it expiring" doesn't fix a clock-skew or credential-expiry root
cause and creates a longer-lived credential-equivalent artifact that's a
larger security exposure if the URL leaks (e.g., via logs, browser
history, or a referrer header) -- fix the actual mismatch instead of
widening the window. Also, disabling S3 Block Public Access or loosening
the bucket policy broadly to make a pre-signed URL "just work" removes
protections that likely exist for good reason; scope any policy change
narrowly to the specific condition actually needed.

## Verify
Regenerate a pre-signed URL after fixing clock sync/policy/credential
issues and use it from the actual production environment/path
(including any proxy/CDN) within its intended validity window, confirming
success. Then deliberately test both edges: a request just before expiry
(should succeed) and just after (should fail with a clean `expired`
error, not a signature mismatch), confirming the expiry behavior is now
predictable.
