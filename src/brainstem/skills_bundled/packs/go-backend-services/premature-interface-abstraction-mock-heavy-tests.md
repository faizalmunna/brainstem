## Symptom
Nearly every concrete type in the codebase has a corresponding interface
defined alongside it, almost always with exactly one production
implementation. Tests are dominated by mock setup (often generated by
`mockgen`/`moq`) rather than real behavior, and a change to a struct's method
signature ripples into every interface definition, every mock
implementation, and every test that constructs that mock -- turning a small
change into a large, mechanical diff across many files with little actual
value added.

## Likely causes
1. **Interfaces defined at the producer side "for testability" by default**,
   following a rule-of-thumb from another language/community without Go's
   specific idiom in mind -- Go convention is to define interfaces at the
   *consumer* side, narrowly, only where genuinely needed for substitution
   (a real second implementation, or a test double for an expensive/
   external dependency), not preemptively for every type.
2. **Mocking used as the default test strategy even for cheap, deterministic,
   in-process dependencies** (a pure function, an in-memory struct with no
   I/O) that could just be exercised directly -- mocks earn their cost when
   the real dependency is slow, non-deterministic, or external (network,
   time, randomness), not as a blanket default.
3. **A single implementation "interface everything" pattern inherited from a
   framework or an internal style guide/template** that was copied without
   revisiting whether the abstraction is pulling its weight in this
   particular codebase.
4. **Fear of a future second implementation that hasn't materialized** --
   the interface was added speculatively ("what if we swap databases
   someday") rather than in response to an actual, current need for
   substitution.

## Diagnose
- For each interface in the codebase, count its production implementations
  -- `grep`/an IDE's "find implementations" for the interface type. An
  interface with exactly one non-test implementation, that has had exactly
  one implementation since it was introduced, is a strong candidate for
  unnecessary abstraction.
- Check where each interface is *defined* relative to where it's
  *consumed* -- if it's defined in the same package as its sole
  implementation (producer-side) rather than in the package that calls it
  (consumer-side), that's a sign it was added preemptively rather than
  pulled out in response to a real need at a call site.
- Sample a handful of recent PRs/diffs that changed a widely-used struct's
  method and measure how many files changed purely to update
  interface/mock definitions versus files with actual logic changes -- a high
  ratio of mechanical mock-update files to logic files quantifies the cost.
- Check test files for the ratio of mock setup/assertion code to real
  assertions about behavior -- tests that mostly verify "mock X was called
  with args Y" rather than "the system produced the correct output" are a
  sign the abstraction is being tested instead of the behavior.

## Fix
Default to depending on concrete types directly, and introduce an interface
only at the point a second real implementation exists or a genuine test
seam is needed (an external dependency that's slow/non-deterministic/costly
to run in tests -- a database, a third-party API, the system clock). Define
that interface in the *consuming* package, scoped to only the methods that
consumer actually calls, not mirroring the full concrete type's method set:
```go
// in the consumer package, not the database package
type UserFetcher interface {
    GetUser(ctx context.Context, id string) (*User, error)
}
// consumer depends on this narrow interface; the concrete *db.Store
// satisfies it structurally with no explicit declaration needed
```
For genuinely expensive/external dependencies, this narrow, consumer-defined
interface is exactly the right tool -- the fix here is scope and placement,
not eliminating interfaces altogether. For everything else, pass the
concrete struct and test against real (in-memory, fake, or actually-run)
behavior instead of a generated mock.

## Pitfalls
- Swinging to the opposite extreme -- removing every interface, including
  the ones genuinely wrapping slow/external dependencies -- makes those
  specific tests slow or flaky again; the fix is selective, not absolute.
- A narrow interface defined at the consumer can still accidentally grow
  back into a mirror of the full producer type over time as more methods
  get added to satisfy new callers -- periodically check whether the
  interface's method set still matches only what's actually used, not
  everything the concrete type happens to expose.
- Removing an interface that's used for legitimate compile-time API
  boundary enforcement between two teams/modules (not just testability)
  can remove an intentional decoupling point -- confirm the interface's
  purpose (testability vs. genuine architectural boundary) before removing
  it.

## Verify
After narrowing or removing an unnecessary interface, confirm the affected
tests still pass using the real concrete type (or a much smaller number of
purpose-built fakes only where genuinely needed), and measure that a
subsequent small method-signature change to that struct now touches
noticeably fewer files than the equivalent change did before, since there's
no parallel interface/mock definition to update in lockstep.
