## Symptom
A test or piece of output-producing code passes most of the time but
occasionally fails or produces differently-ordered output with no code
change and no obvious concurrency involved -- string concatenation from a
`map[string]T`, a generated report, a comparison of two slices built by
ranging over a map, or a batch operation whose processing order seems to
shift between runs. The flakiness is often blamed on "test flakiness" or
timing before anyone notices every failure traces back to a `for k, v :=
range someMap`.

## Likely causes
1. **Code ranges over a `map[K]V` and appends keys/values to a slice, then
   later compares that slice for equality or joins it into a string**,
   assuming a stable order -- Go deliberately randomizes map iteration order
   per iteration (since Go 1.0) specifically to prevent code from
   accidentally depending on it, so this is guaranteed to eventually surface,
   not a rare edge case.
2. **A test builds expected output by iterating a map on the test side too**,
   masking the bug locally (both sides "happen" to iterate in the same
   random order within a single process run) until run against a different
   build, a different Go version, or a CI environment with different map
   internals/hash seeding.
3. **JSON, string, or log output is generated by ranging over a map directly**
   instead of sorting keys first, so two runs of the same program produce
   byte-different but semantically-equivalent output -- this breaks
   golden-file tests, diff-based log comparisons, and caching keyed by exact
   output bytes.
4. **Reliance on "insertion order" from a map**, carried over from another
   language's ordered-dict/LinkedHashMap semantics -- Go maps have never
   guaranteed insertion order, so code written by someone assuming that
   semantic (or ported from Python/JS) silently breaks the moment more than
   one entry with meaningful relative order is involved.

## Diagnose
- Grep for `for .* := range` where the ranged variable is a `map[...]`
  type, then check what happens to the loop's output -- if it's appended to a
  slice, concatenated into a string, or otherwise order-sensitive, that's the
  candidate.
- Run the suspect test or program in a loop (`for i in $(seq 1 50); do go
  test -run TestName -count=1 ./...; done` or `go test -count=100
  -run TestName`) -- map order flakiness usually reproduces within a handful
  of runs since each process re-randomizes its map seed, unlike a genuine
  race condition which may need `-race` or much higher iteration counts.
- Add a temporary print of the raw iteration order (`fmt.Println(k)` inside
  the range) across a few runs of the same binary -- if the printed order
  changes between separate process invocations but not within a single
  process's repeated iteration of the same unmodified map, that confirms
  it's Go's per-hash-seed randomization, not something else.
- For golden-file/snapshot test failures, diff the actual vs. expected output
  specifically for reordering (same lines, different sequence) rather than
  content differences -- that pattern strongly implicates unsorted map
  iteration in whatever produced the output.

## Fix
Wherever order matters for output or comparison, explicitly sort the keys
before iterating, rather than relying on any incidental map behavior:
```go
keys := make([]string, 0, len(m))
for k := range m {
    keys = append(keys, k)
}
sort.Strings(keys)
for _, k := range keys {
    process(k, m[k]) // deterministic order every run
}
```
For test assertions comparing map-derived collections, compare as sets/maps
directly (`reflect.DeepEqual` on the maps themselves, or a testify
`ElementsMatch`-style assertion) instead of converting to an ordered slice
and comparing with strict equality -- this sidesteps the ordering question
entirely for cases where order was never actually meaningful.

## Pitfalls
- Sorting keys "just in case" everywhere a map is touched adds needless
  overhead in genuinely order-independent contexts (e.g. summing values,
  building a lookup) -- apply sorting specifically where output is compared,
  displayed, or hashed, not as a blanket habit.
- Fixing the immediate output-generation code but leaving the *test* that
  masked the bug still building its expected value by iterating a map the
  same unsorted way -- both sides need the fix, or the test will pass by
  coincidence again the moment iteration order happens to realign.
- Reaching for a third-party ordered-map type as a first response when plain
  sort-before-iterate solves the actual problem with no new dependency --
  reserve ordered-map data structures for cases that genuinely need
  insertion-order-preserving *storage*, not just deterministic iteration at
  output time.

## Verify
Run the affected test with `go test -count=100 -run TestName ./...` (or
wrap the specific function in a loop across many fresh process invocations,
since map seed is per-process) before and after the fix -- before, expect
occasional reordering-driven failures within that count; after, expect zero
failures across all runs, confirming the fix removed the dependency on
iteration order rather than merely reducing its likelihood.
