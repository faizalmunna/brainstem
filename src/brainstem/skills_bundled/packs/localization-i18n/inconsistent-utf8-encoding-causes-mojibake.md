## Symptom
Text containing non-ASCII characters (accented Latin letters, CJK characters, Cyrillic, emoji, curly quotes from a word processor) displays as garbled symbol sequences (classic mojibake like `Ã©` instead of `é`, or `â€™` instead of `'`), literal `?` replacement characters, or boxes/tofu glyphs -- sometimes only after the data round-trips through storage (looks fine on entry, garbled on the next page load), sometimes only in certain contexts (fine in the app UI, garbled in an exported CSV or a sent email), which points to an encoding mismatch at a specific layer rather than a universal failure.

## Likely causes
1. **A layer in the stack defaults to a non-UTF-8 encoding** -- a MySQL table/column created with `latin1` (or the deceptive `utf8` alias in MySQL, which is actually a 3-byte-max encoding that silently truncates or corrupts 4-byte characters like emoji and some CJK/mathematical characters, unlike true `utf8mb4`), an HTTP response missing `charset=utf-8` in its `Content-Type` header, or a file read/written without an explicit UTF-8 encoding falling back to a platform default (e.g. Windows-1252 on Windows, ASCII in some minimal environments).
2. **Data is decoded with the wrong source encoding at some point in the pipeline**, so bytes that were correctly written as UTF-8 get misinterpreted as Latin-1 (or vice versa) on read -- this produces the classic double-encoding mojibake pattern where the misinterpreted bytes are then themselves re-encoded as UTF-8, compounding the corruption on each additional round-trip.
3. **A boundary between two systems (a legacy import job, a third-party API integration, a copy-paste from a word processor with smart quotes, a CSV export opened in a tool that assumes a different default encoding) introduces bytes in a different encoding than the rest of the pipeline expects**, and nothing in the pipeline validates or normalizes encoding at that ingestion point.
4. **The database connection itself negotiates a different encoding than the column's stored encoding**, independent of what the column is defined as -- e.g. a MySQL client connection defaulting to `latin1` while the table is `utf8mb4` silently transcodes on write and read, corrupting data even though the schema itself is configured correctly.

## Diagnose
- Identify exactly which layer introduces the corruption by checking the raw bytes at each boundary: inspect the raw HTTP response bytes/headers for `charset=utf-8`, inspect the database column's actual character set (`SHOW CREATE TABLE` in MySQL, checking for `utf8mb4` vs `utf8`/`latin1`), and inspect the database connection's negotiated charset separately from the column definition (`SHOW VARIABLES LIKE 'character_set%'` in MySQL) since these can differ.
- Reproduce with a known test string containing characters outside the Basic Latin range in increasing byte-width (an accented Latin character, a CJK character, and a 4-byte character like an emoji or certain rare CJK ideographs) and trace it through each layer (input, API request, database write, database read, API response, frontend render) to find the exact hop where it first becomes corrupted.
- Recognize the specific corruption pattern: `Ã©` for `é` or `â€™` for a curly apostrophe indicates UTF-8 bytes misread as Latin-1/Windows-1252 (classic double-encoding); a literal `?` or a black diamond with a question mark indicates the bytes were actually lost/replaced (lossy transcoding through an encoding that can't represent the character, such as true `latin1` or MySQL's `utf8`), which is not recoverable from the corrupted data alone and requires fixing the source and re-importing.
- Check whether the corruption appears immediately on input (points to a decode issue on the write path) or only reappears later, e.g. after a export/import cycle or a specific integration (points to that specific boundary rather than the primary read/write path).

## Fix
Standardize on UTF-8 (specifically `utf8mb4` in MySQL, not the legacy 3-byte `utf8` alias) at every layer of the stack -- database column/table charset and collation, the database connection charset, HTTP `Content-Type` headers with an explicit `charset=utf-8`, file I/O with explicit UTF-8 encoding specified (never relying on a platform default), and any serialization format in between -- so there is exactly one encoding in use end-to-end with no silent transcoding at any hop. For data already corrupted by lossy transcoding (characters actually replaced, not just misdisplayed), the fix has to happen at the source: identify and correct the ingestion point, and re-import from the original source data if the lossy corruption already overwrote the correct bytes, since a `?` replacement character cannot be reverse-engineered back to the original character.

## Pitfalls
- Attempting to "fix" already-corrupted double-encoded data by running it through another encoding conversion in the application layer (a common but fragile workaround) can appear to fix simple cases while further corrupting edge cases, and doesn't address the root misconfiguration that will keep producing new corrupted data going forward -- fix the pipeline's encoding configuration first, then handle historical data as a separate, deliberate remediation.
- Assuming "we use UTF-8" because the codebase or ORM defaults to it in most places without verifying the actual database column charset and the connection charset independently -- MySQL's `utf8` (not `utf8mb4`) is a common trap because it looks correct by name while silently mangling any 4-byte character.
- Fixing the primary application read/write path but missing secondary export paths (CSV downloads, PDF generation, email sending, log files) that use a different serialization step with its own encoding default, leaving mojibake in those specific outputs even after the main data path is corrected.

## Verify
Write a test string containing at least one multi-byte character from each relevant category (an accented Latin character, a CJK character, and a 4-byte character such as an emoji) through the full pipeline end-to-end -- input form, API request, database write, database read, API response, and final render/export -- and confirm the exact same string comes out the other end unchanged at every hop, not just at the final display step, by comparing byte sequences at each boundary rather than only eyeballing the rendered result.
