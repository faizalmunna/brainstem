## Symptom
When a RAG answer is wrong, the team's only diagnostic signal is the final answer itself (a user complaint, a thumbs-down, an eyeballed "that's not right") -- there's no way to quickly determine whether the retrieved chunks were wrong/insufficient (a retrieval problem) or the LLM had good context but generated a bad answer anyway (a generation problem). Debugging every failure requires manually re-reading raw retrieved chunks case by case, which doesn't scale and produces inconsistent conclusions between different engineers looking at the same failure.

## Likely causes
1. **The project only ever built an end-to-end eval (final answer vs. expected answer)** because that's the metric that matches the user-facing product goal, without a separate intermediate checkpoint that scores retrieval in isolation -- a natural but incomplete evaluation design.
2. **No "gold" or judged mapping exists from query to expected-relevant-chunk(s)**, which is the actual prerequisite for any retrieval-specific metric (precision@k, recall@k, MRR, NDCG) -- without it, retrieval can't be scored at all, only guessed at qualitatively.
3. **Retrieval and generation are treated as one opaque unit in the codebase/observability setup** -- logs and traces capture the final prompt and response but don't separately expose and store which chunks were retrieved and at what rank, making even manual post-hoc analysis slower than it needs to be.
4. **The team conflates "user satisfaction" with "answer correctness" with "retrieval correctness"** as a single undifferentiated quality signal, so even when data exists (thumbs down, tickets), it isn't structured in a way that lets these three questions be answered independently.

## Diagnose
- Check whether any stored eval dataset maps a query to a specific expected chunk ID or set of chunk IDs (not just an expected final answer string) -- its absence directly confirms this gap.
- Check observability/logging for a sample of recent production queries: is the actual list of retrieved chunks (with scores and ranks) captured and queryable, or only the final LLM response?
- Take 10 recent "bad answer" reports and try to classify each as retrieval-fault vs. generation-fault using only currently available logs/data -- if this requires manually re-running the retriever and reading raw chunks each time rather than looking up an existing recorded eval, that confirms the tooling gap concretely.

## Fix
Build a small, curated retrieval-specific benchmark: a set of real or representative queries each paired with the chunk ID(s) that should be retrieved to answer them correctly (sourced from support tickets, known documents, or SME review -- not synthesized guesses). Compute standard retrieval metrics against it (precision@k, recall@k, Mean Reciprocal Rank, and/or NDCG if graded relevance is available) as an automated, re-runnable job, separate from any end-to-end answer-quality eval. In production logging/tracing, always record the retrieved chunk IDs, scores, and ranks alongside the final prompt and response for every query (or a sampled subset), so any later "bad answer" investigation can look up what was actually retrieved without re-running anything. Treat the two evals as a diagnostic pair: when end-to-end quality is bad, check the retrieval-specific score first -- good retrieval score + bad end-to-end score isolates the fault to generation; bad retrieval score explains the end-to-end failure directly.

## Pitfalls
- Building the retrieval benchmark from synthetic queries generated by an LLM rather than real user queries or real support tickets, producing a benchmark that doesn't reflect actual query patterns and gives a false sense of coverage.
- Treating precision@k or recall@k as sufficient alone without also tracking rank position (MRR/NDCG) -- a system can have perfect recall@10 while consistently burying the right answer at rank 9, which still produces bad end-to-end answers if downstream top-k or re-ranking assumes better-than-that ranking quality.

## Verify
Confirm the retrieval benchmark runs as an automated job producing a precision/recall/MRR score, and pick 3 recent real "bad answer" incidents to retroactively classify using the new retrieval score plus recorded production retrieval logs -- confirm each can now be attributed to retrieval-fault or generation-fault without manual re-investigation from scratch.
