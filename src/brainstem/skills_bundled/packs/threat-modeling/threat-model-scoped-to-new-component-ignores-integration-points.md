## Symptom
A new service or component gets a dedicated threat modeling session, and the resulting document is thorough about that component's own internals — its own inputs, its own data store, its own auth checks. But a real threat later surfaces specifically in how it interacts with an existing system it was built to integrate with: a shared assumption about who validates a field that neither side actually validates, a legacy system that trusts any caller from the new service's IP range without re-checking identity, or a race condition that only occurs because the new component and an existing one both write to the same downstream resource. The gap wasn't inside either system's own model — it was in the seam between them, which neither document's scope included.

## Likely causes
1. **Threat modeling scoped to "this project's" deliverable**, drawn around exactly the code/infrastructure being newly built, treating everything it connects to as an already-trusted, already-analyzed black box — because the existing system was presumably threat modeled at some point in the past, its side of the interaction isn't re-examined in light of the new connection.
2. **The existing system's original threat model (if one even exists) predates this integration** and was never revisited to ask "does a new caller with this access pattern change any of my prior assumptions" — so neither side's documentation captures the combined behavior, only each side's behavior in isolation.
3. **Ownership split discourages cross-boundary analysis** — the new component's team threat models their own service because that's what they're accountable for delivering; the legacy system's team, if they're even in the room, may see the integration as the new team's problem to get right, and nobody treats the interaction itself as a first-class thing to be modeled.
4. **API/interface contracts are assumed rather than verified during modeling** — the session reasons about the integration using the documented API contract ("the endpoint requires an auth token and validates input") rather than checking the actual current behavior of the existing system, which may have drifted from its documentation or never enforced what the contract claims.

## Diagnose
1. Check whether the threat model explicitly lists the integration points (specific APIs, shared databases, message queues, shared auth tokens) between the new component and existing systems as their own analyzed items, distinct from either system's internal threats — if integration points appear only as unlabeled arrows on a diagram with no threats attached to them specifically, they weren't actually analyzed.
2. For each integration point, verify directly (not from documentation) what validation, authentication, or authorization the existing system actually performs on requests coming from the new component — read the actual code path or make a test call, rather than trusting the API contract as written.
3. Ask both teams (new component's and existing system's) independently who they believe is responsible for validating a specific piece of shared data or enforcing a specific check at the integration boundary. Divergent answers reveal an assumed-but-unverified division of responsibility — a classic source of seam threats.
4. Look for any threat in the model that references data or trust *crossing* between the two systems (not just data flowing one direction as an input) — if every threat is contained within one system's boundary and none describe a two-way interaction failure (e.g., what happens if the new system times out mid-transaction and the legacy system doesn't know), that category is missing.

## Fix
Explicitly model the integration surface as its own subject, separate from either system's internal threat analysis — list every point of contact (API calls, shared data stores, shared credentials, shared queues) and, for each, verify actual current behavior on both sides rather than relying on the documented contract. Require representation from both the new component's team and the existing system's team (or at least someone who knows the existing system's actual current behavior) in the same session when the integration is non-trivial, so assumptions about "who validates what" are stated out loud and checked against reality rather than each side assuming the other handles it. Treat "what happens when this integration behaves unexpectedly" (timeout, partial failure, unexpected input format, replay of a stale token) as its own threat category to walk through explicitly, since these seam failures are exactly the kind that isolated per-system analysis structurally can't surface.

## Pitfalls
A frequent shortcut is adding "integration security" as a single bullet point in the new component's threat model without actually tracing specific data and trust flow across the boundary — a token acknowledgment that the integration exists isn't the same as analyzing it. Another pitfall: assuming that because the existing system has its own (possibly old) threat model, its side of this specific new interaction is already covered — an existing system's prior threat model was written against the callers and assumptions that existed when it was made, not against a caller that didn't exist yet.

## Verify
For the integration between the new component and each existing system it connects to, confirm the threat model contains at least one threat that specifically describes a failure mode arising from the interaction itself (not just from either system's internals), and confirm the validation/auth behavior assumed at that boundary was checked against the existing system's actual current implementation, not just its documented contract.
