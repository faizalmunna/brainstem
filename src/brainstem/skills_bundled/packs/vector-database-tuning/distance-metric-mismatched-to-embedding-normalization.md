## Symptom
Similarity scores returned by the index are suspicious in a specific way: either they're all clustered in a narrow, uninformative range (e.g. every result scores 0.98-0.99 similarity regardless of actual relevance), or the ranking order looks close to random relative to manual judgment of relevance, even though the embeddings themselves are known to be good quality (verified by checking pairwise similarity of known-similar and known-dissimilar text pairs using a different, trusted method). This tends to appear right after switching embedding models or after copying an index config from a different project without checking metric compatibility.

## Likely causes
1. The index is configured for Euclidean (L2) distance but the embedding model produces normalized vectors (unit length), where L2 distance and cosine similarity are monotonically related only if vectors are truly on the unit sphere -- if normalization was skipped somewhere in the ingestion path (e.g. only applied to query-time embeddings but not to stored ones, or vice versa), L2 distances become dominated by magnitude differences that carry no semantic meaning.
2. The index is configured for cosine similarity, but the embedding model was specifically trained for dot-product similarity (common with some retrieval-optimized models, e.g. certain dual-encoder models trained with in-batch negatives using unnormalized dot product) -- normalizing before comparison throws away magnitude information the model actually encodes meaningfully.
3. A model swap happened (upgrading embedding model versions or switching providers) without checking whether the new model's expected distance metric matches the old one -- different embedding models are trained/documented for different metrics, and the index config wasn't updated to match, silently producing degraded-but-not-erroring results (this is metric mismatch, distinct from the sibling RAG-pack skill about full embedding-model version mismatch between index and query time, which covers using two different model versions/dimensions entirely).
4. Vectors are stored unnormalized while the index's internal implementation assumes normalized input for its cosine computation shortcut (some engines compute cosine as a dot product internally for speed, which is only correct if vectors are pre-normalized to unit length before insertion) -- this produces a metric that's neither correct cosine nor correct dot-product.

## Diagnose
1. Check the embedding model's documentation/model card for its stated intended similarity metric -- most published embedding models (OpenAI, Cohere, Sentence-Transformers variants) explicitly state whether cosine, dot-product, or L2 was used during training/contrastive loss, and this is not interchangeable by convention alone.
2. Check the actual index/collection config for which metric is active (e.g. pgvector's `vector_cosine_ops` vs `vector_l2_ops` vs `vector_ip_ops` operator class, Milvus/Qdrant/Weaviate's explicit `metric_type` field) and compare against step 1.
3. Compute the L2 norm of a sample of stored vectors directly -- if norms vary substantially (not clustered near 1.0) but the index is configured for cosine or IP assuming normalization, that's the mismatch; if norms are already ~1.0 for all vectors, cosine and normalized-dot-product should agree and normalized L2 becomes a monotonic transform of cosine (so metric choice matters less, but consistency of normalization end-to-end still matters).
4. Take a small set of known duplicate/near-duplicate and known-unrelated text pairs, embed them, and compute similarity under each candidate metric manually (outside the index) to see which metric actually separates the two groups -- this directly tests metric-model fit independent of any index software.

## Fix
Set the index's distance metric to exactly what the embedding model's documentation specifies, not by convention or by copying another project's config, and apply the same normalization treatment consistently to both stored (indexed) vectors and query vectors -- normalize both or neither, never one but not the other. When switching embedding models or providers, treat the distance metric as part of the model's contract that must be re-verified, not an independent infra setting that carries over. If the engine's cosine implementation is a normalized-dot-product shortcut internally, normalize vectors explicitly at write time rather than relying on the engine to do it implicitly, so the behavior is visible and testable.

## Pitfalls
Don't assume cosine similarity is always the "safe default" -- for models trained explicitly on raw dot product with meaningful magnitude (magnitude sometimes encodes something like passage informativeness or length in certain retrieval-tuned models), forcing normalization and cosine can measurably hurt ranking quality relative to what the model's training actually optimized for. Also don't fix a suspected metric mismatch by re-embedding only the query side or only new documents going forward -- a mixed index (old vectors under one normalization convention, new vectors under another) produces inconsistent, hard-to-debug ranking that's worse than either convention applied uniformly.

## Verify
Re-run the known-duplicate/known-unrelated pair comparison from Diagnose step 4 directly against live index queries (not just the offline manual computation) and confirm known-duplicates rank at the top with a clearly separated score from known-unrelated pairs; also confirm the recall@k ground-truth benchmark (shared with the other tuning skills in this pack) improves after correcting the metric, since a metric mismatch shows up as a real recall regression, not just a cosmetic score-range issue.
